## 失败与观察

1. 首次免 Root 写入 EC 后，立即回读触发 `VolumeWriteState.awaitPath` 的写入未完成保护。ADB `content read` 随后显示空文件句柄异常。等待后校验成功，因此这次不能认定为文件内容错误；测试脚本已补充等待。
2. 随后的卷信息查询曾超过 120 秒，稍后恢复。尚未证明死锁，也未确认空间统计是否为主要耗时来源。
3. 免 Root 覆写 EX 卷时，FatFs 在文件 offset 0 报错：`Batch block write failed: expected 131072, got -1`。随后出现 USB bulk IN/OUT 失败、SCSI 重试耗尽，native fd 通道被标记为 poisoned，写入客户端收到 EPIPE。
4. 对失败卷请求正常安全关闭，返回 `success=false`，明确提示文件传输失败；未强行终止应用或复位设备以绕过此保护。

这里的 128KiB 是逻辑批量写请求，不是单次 USB bulk 大小；当前 bulk 传输仍按最多 16KiB 切分。不能仅凭请求长度认定超限。

源码审查另确认：`UsbStorageManager.UsbBlockDeviceWorker` 的异步分支在写任务入队后即返回成功 ACK，SCSI 失败会稍后才传播。它存在完成语义风险，**但尚不能认定为本次 bulk 失败的已证实根因**；需要进一步核对失败阶段、分块及超时。不能用延长超时或提前报成功来消除测试失败。

## 重连恢复与同步写入对照

2026-10-24，充电后恢复测试，开始时电量 45%。

1. 重连后六卷在免 Root 模式恢复。通过主页执行免 Root → Root，最终 Release 正常重启，六个会话路径均为 `/dev/block/`，保存凭据及附属记录哈希与初始记录一致。
2. Root 下核验旧测试文件：EC、FC、FX、NC、NX 均匹配最后一次已确认的数据；EX 仍为 2MiB，但哈希既不匹配完整旧数据，也不匹配失败写入所用的新数据。随后六个旧测试文件全部删除。
3. 新建一个独立的 EX 测试文件，Root 写入并校验 2MiB 基准数据。通过现有接口临时关闭 `use_pipelined_write`，从主页切到免 Root；整个对照过程没有人工重插设备。
4. 在同一 EX 分区覆写另一份 2MiB 数据。写入命令返回约 **6.20 秒**，完成写入与回读校验约 **30.91 秒**，长度和 SHA-256 一致。
5. 再通过主页切回 Root，六个保存凭据会话恢复；该文件的 SHA-256 仍与免 Root 写入数据一致，跨会话持久性校验通过。随后删除这个对照文件。
6. 恢复流水线设置后，从主页正常弹出全部六卷，确认会话数为 0；再对已核实的 PSSD SCSI host 重新发现设备，恢复原 Root 六卷。

**对照结论：关闭流水线时，EX 的这一次 2MiB 写入、完整界面往返、持久性校验和后续 Root 正常弹出通过。** 这支持继续排查异步写入确认路径，但单次对照及重新连接的设备状态不足以证明早 ACK 是唯一根因，尚未实施应用修复。

脚本观察：曾在切换时向正在退出的 Provider 进程发起查询，ADB 查询超过 120 秒；此时设备实际已完成重启。等待新 PID 和目标模式后再查询成功。该脚本时序问题与前述 EX 写入错误分开记录，不能据查询超时单独认定应用死锁。

最终恢复状态：Root 六卷已解锁，全部 **7 个**隔离测试文件均确认不存在；临时流水线偏好键恢复为原先不存在的状态，运行值为默认 `true`；原设置与凭据哈希一致，Wi-Fi 正常，电量 43%。默认异步写入失败仍是发布阻塞项。

## 写入确认修复后的复测

2026-10-24，完整修复包对应 `74cf4ec`，Release / versionCode 129，无 DEBUGGABLE 标志。三个修复分别为：

- `d18b055`：fd 通信每个阶段采用单调时钟绝对期限，响应预算 60 秒；部分进度和信号中断不会重置期限，失败仍关闭并 poison 通道。
- `8523312`：USB block worker 在实际读写完成后才确认，错误保持到该通道结束；移除依赖提前确认的 USB 异步流水线选项，保留 SAF 缓冲选项和最多 16KiB 的 USB bulk 切分。
- `74cf4ec`：USB 分区始终使用内核路径，避免 vold 稍后发布同一分区的别名时，扫描误关原有会话。

本地验证：**88 项 Release JVM 测试、三种架构 Release 构建、lintVitalRelease 均通过**。新增测试覆盖完成前不返回写入成功、失败后拒绝后续读写/同步、不返回不完整读取、分区别名稳定性。平板 socketpair harness 的六组测试通过，覆盖迟到响应、部分帧、poison 后拒绝复用和延迟完成；该短时测试用编译参数将响应预算缩为 1000ms，不访问块设备。

### 仍失败：NX 写入期间的 CSW 超时

第六个卷 NX 覆写时失败，NTFS writer 在文件 offset 1048576 报 `Batch block write failed: expected 524288, got -1`。新增阶段日志显示：

1. 首个失败是 bulk IN，endpoint 129，**requested=13**，约 **5048ms** 后返回 -1，框架后的 errno 查询为 0；对应 BOT 的 CSW 状态响应。
2. 随后 libaums 重发整条命令，bulk OUT 的 **31 字节 CBW** 连续约 5 秒超时；不是单次 512KiB USB bulk 超限。
3. native 通道被 poison，文件传输失败。停止本地后续测试，没有执行 EX 两轮重复覆写、持续刷新压力测试或免 Root → Root 的收尾往返。
4. 请求正常关闭 `usb://2002/p6` 后，ADB 调用超过 **120 秒**，没有取得成功结果。未 force-stop 应用、强制丢弃会话或主动复位设备。
5. 非致命线程堆栈确认有 USB worker 正在 SCSI 初始化/读取重试；Provider 的线程还在 `f_getfree` 读盘。空间统计访问异常通道会放大查询/关闭等待，这一现象现有堆栈证据；不能把所有等待都归为同一种锁死。

**结论：提前 ACK 的完成语义缺陷已修复，但底层异常仍可复现，不能认定它是旧 EX 故障的唯一原因。** 当前证据定位到 CSW 阶段；状态端点停滞、真实超时或桥接固件原因尚不能区分。下一步应核对 CSW 失败后的 BOT 状态恢复、整条命令重发与缓冲位置，以及可靠的 USB 错误码，而不是仅继续加长超时。
